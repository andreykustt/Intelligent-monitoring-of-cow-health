# Запуск и эксплуатация

## Локальный запуск

Требуются Docker Engine и Docker Compose. Для проверок на хосте — Go согласно `services/go.mod`, Node 22, Python 3.

```sh
python3 scripts/init_env.py
docker compose config -q
docker compose up -d --build
```

Открыть http://localhost:8080. Логины: `admin`, `operator`. Соответствующие пароли находятся **только** в локальном `.env` (`ADMIN_PASSWORD`, `OPERATOR_PASSWORD`). Не публиковать этот файл. Генератор конфигурации не перезаписывает существующий файл. При ручном задании паролей БД/брокера используйте URL-safe символы или URL-encoding в URL подключения. Пароли пользователей — 12–72 байта.

Seed создаёт учебную ферму, 200 животных и датчики. Повтор seed не сбрасывает изменённые пароли. Смена `.env` не меняет уже созданные учётные записи/пароли существующих volumes. Для пользователя используйте экран сброса пароля; настройки БД/брокера меняйте средствами соответствующего сервиса.

## Проверки

```sh
cd services
go test ./...
go vet ./...
cd ../frontend
npm ci
npm run generate:api
npm run lint
npm run build
cd ..
python3 scripts/smoke.py
python3 scripts/demo_replay.py
```

Браузерные тесты: из frontend `npx playwright install --with-deps chromium`, затем `npm run test:e2e`. Тесты читают локальные демо-пароли из `.env`, не выводят их. Smoke создаёт новые учебные записи; браузерный тест администратора регистрирует тестовое животное. Используйте отдельную демонстрационную БД.

ML проверяется при сборке образа: offline training, pytest и ruff. Повторно: `docker compose exec ml-service python -m pytest -q` и `docker compose exec ml-service python -m ruff check .` (runtime cache goes to /tmp). Модель не переобучается в HTTP запросе.

## Демонстрация

1. Администратор открывает «Симуляции» и запускает 200 животных, 9 метрик с интервалом 5000 мс. Это целевые 360 событий/с, не гарантия фактической скорости.
2. Оператор открывает монитор и карточку. Значения появляются после commit worker; 202 ingest означает только подтверждение брокера.
3. Добавляет ручное наблюдение, исправляет, открывает историю.
4. Для заполнения часового ML-окна без часа ожидания выполните `python3 scripts/demo_replay.py`: 180 исторических синтетических показаний воспроизводятся со скоростью 100x, примерно за 36 секунд. После обработки analyzer уведомление появится для COW-001.
5. Подтверждает и закрывает уведомление с комментарием.
6. `docker compose stop ml-service`: новые измерения продолжают поступать. После `docker compose start ml-service` сохранённые задания анализа повторяются.
7. Отключает/включает сеть браузера: WS переподключается, REST повторно загружает актуальные данные.

## Остановка и диагностика

```sh
docker compose ps
docker compose logs --tail 100 api-service data-worker ingest-service ml-analyzer
docker compose down
```

`down` сохраняет volumes. Не используйте `down -v` для обычной остановки. Внутренние сервисы не имеют опубликованных портов. Веб-приложение привязано к loopback; при выносе наружу настройте HTTPS, APP_ORIGIN и COOKIE_SECURE=true, не открывайте БД/брокер наружу.

При недоступности брокера ingest возвращает 503; симулятор повторяет тот же event_id до 5 раз, затем завершает запуск с ошибкой. Новый процесс симулятора не возобновляет неоднозначный старый запуск: отмечает его failed. Создайте новый запуск. Настройка интервалов не меняет число животных/режим работающей симуляции. Продолжительность считается по настенным часам, включая паузу.

Worker ACK выполняется после commit. Некорректные/неизвестные события направляются в `telemetry.dead`; повторяемые ошибки ограничены delivery limit quorum-очереди. Outbox и анализ используют сохранённое состояние, WS остаётся best-effort.

## Миграции и резервная копия

Один migration runner и PostgreSQL advisory lock. API не меняет схему при запуске. Новые миграции применять перед сервисами. Down SQL — операторский откат схемы; начальная down-миграция удаляет данные и требует резервной копии. Автоматический rollback не выполняется.

Резервная копия (из корня, credentials берутся внутри контейнера):

```sh
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backup.dump
```

Восстановление сначала проверять на отдельной БД:

```sh
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner' < backup.dump
```

Не коммитьте backup.dump. Retention и автоматическое удаление истории не включены; контролируйте размер volumes. Для миграций существующей инсталляции не редактируйте применённую миграцию — добавляйте новую.
