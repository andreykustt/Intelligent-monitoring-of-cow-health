# Стадо — интеллектуальный мониторинг состояния коров

**Cow Health Monitor** — учебное веб-приложение для наблюдения за показателями крупного рогатого скота. Оно собирает синтетическую или воспроизводимую из истории телеметрию, хранит ручные наблюдения, показывает графики и уведомляет о необычных изменениях показателей.

Проект реализует MVP с двумя ролями: **администратор** и **оператор**. Реальные аппаратные датчики не подключаются. **Обнаруженная аномалия не является диагнозом, а отсутствие аномалии — заключением о здоровье животного.**

## Возможности

- **Монитор стада:** список животных, поиск, серверные фильтры, сортировка и постраничная выдача.
- **Карточка животного:** последние показатели с единицами и свежестью, история на графиках, общий журнал измерений, результатов анализа и уведомлений.
- **Обновления без перезагрузки:** доставка событий через WebSocket после сохранения измерений в базе данных.
- **Ручные записи:** доение, визуальный осмотр, лабораторные результаты, упитанность и состояние копыт, ветеринарный осмотр. Исправления сохраняют версии, причину, автора и время.
- **Симулятор:** генерация показателей или воспроизведение исторических записей с сохранением времени измерения; настройка частот, сценариев и длительности, пауза, продолжение и остановка.
- **Анализ аномалий:** фоновая обработка окон телеметрии учебной моделью Isolation Forest. Состояния «Аномалия», «Нет аномалии» и «Недостаточно данных» различаются.
- **Уведомления:** просмотр, подтверждение и закрытие с комментарием и историей действий.
- **Администрирование:** регистрация и редактирование животных, управление пользователями, ролями и доступом к фермам, блокировка и сброс паролей.
- **Обзор и аналитика:** сводка по стаду, агрегированная история показателей и надои по ручным записям.

### Роли

| Действие | Оператор | Администратор |
|---|:---:|:---:|
| Просмотр животных, показателей и истории | ✓ | ✓ |
| Внесение и исправление ручных записей | ✓ | ✓ |
| Подтверждение и закрытие уведомлений | ✓ | ✓ |
| Создание и редактирование животных | — | ✓ |
| Управление симуляциями | — | ✓ |
| Управление пользователями и доступом | — | ✓ |

Обе роли работают только с разрешёнными фермами. Права проверяются сервером на HTTP-маршрутах и при подключении WebSocket.

## Технологии и устройство системы

| Часть | Технологии |
|---|---|
| Веб-интерфейс | React, TypeScript, Vite, TanStack Query, TanStack Table, ECharts |
| Серверные сервисы | Go |
| Машинное обучение | Python, FastAPI, scikit-learn, Isolation Forest |
| Хранение | PostgreSQL |
| Очередь сообщений | RabbitMQ |
| Доставка обновлений | WebSocket |
| Маршрутизация и запуск | Nginx, Docker Compose |

Путь автоматического измерения:

```text
Симулятор → сервис приёма → RabbitMQ → обработчик → PostgreSQL
                                                       ↓
                                            сохранённое событие
                                                       ↓
                                              API → WebSocket → интерфейс
```

Фоновый анализ читает сохранённую историю и обращается к ML-сервису независимо от приёма телеметрии. Недоступность модели не должна останавливать сохранение измерений. Ответ `202` сервиса приёма означает подтверждение брокера, а не запись в PostgreSQL.

Ручные записи поступают из интерфейса через API непосредственно в PostgreSQL с сохранением аудита. Время измерения, время поступления и время создания записи хранятся отдельно; на границе API используется UTC.

## Требования

Для запуска всего приложения:

- Docker Engine с работающим демоном и Docker Compose;
- Python 3 для создания локального файла настроек;
- свободный локальный порт `8080`;
- доступ к сети при первой сборке для загрузки образов и зависимостей.

Устанавливать Go, Node.js и ML-зависимости на хост для запуска через Compose не требуется. Для локальной разработки нужны Go версии из [services/go.mod](services/go.mod) и Node.js 22 с npm. Для HTTP-проверок необходимы Python 3 и `curl`.

## Быстрый запуск

Все команды этого раздела выполняются из корня репозитория.

### 1. Создать локальные настройки

```sh
python3 scripts/init_env.py
```

Скрипт создаст `.env` на основе `.env.example` и сгенерирует случайные пароли и внутренний токен. Значения не выводятся в консоль. Если `.env` уже существует, скрипт оставит его без изменений и завершится с сообщением — при повторном запуске этот шаг нужно пропустить.

`.env` исключён из Git. В репозитории хранится только шаблон `.env.example`.

### 2. Проверить конфигурацию и запустить сервисы

```sh
docker compose config -q
docker compose up -d --build
```

При запуске выполняются явные SQL-миграции, создаются демонстрационные пользователи, учебная ферма, **200 животных** и датчики. При первой сборке ML-образа обучается учебная модель и выполняются её тесты.

### 3. Открыть приложение

**Адрес: http://localhost:8080**

| Пользователь | Роль | Где найти первоначальный пароль |
|---|---|---|
| `admin` | Администратор | `ADMIN_PASSWORD` в локальном `.env` |
| `operator` | Оператор | `OPERATOR_PASSWORD` в локальном `.env` |

Первоначальное наполнение можно выполнять повторно: существующие пользователи и животные не дублируются. Оно **не сбрасывает пароли** существующих пользователей. Изменение `ADMIN_PASSWORD` или `OPERATOR_PASSWORD` в `.env` не меняет уже сохранённый пароль; для этого используйте административный экран сброса пароля.

Само создание животных не запускает генерацию телеметрии. Для появления показателей создайте симуляцию.

## Первый рабочий сценарий

1. Войдите под `admin` и откройте раздел **«Симуляции»**.
2. Создайте запуск: 200 животных, нужные метрики, интервал 5000 мс, сценарий обычных колебаний или отклонений.
3. Откройте **«Монитор»**: после сохранения измерений появятся значения. Можно войти под `operator` в отдельном профиле браузера и наблюдать тот же поток.
4. Откройте карточку животного, выберите показатель и период графика.
5. Добавьте ручную запись. При необходимости исправьте её с указанием причины и проверьте историю версий.
6. В разделе **«Уведомления»** подтвердите или закройте обнаруженное отклонение с комментарием.

Для анализа требуется история: окно модели составляет один час с минимальным покрытием данных. Сразу после запуска состояние «Недостаточно данных» ожидаемо. Чтобы продемонстрировать анализ без часового ожидания, выполните:

```sh
python3 scripts/demo_replay.py
```

Скрипт запускает воспроизведение 180 синтетических исторических показаний для `COW-001` со скоростью 100×, примерно за 36 секунд. Результаты появляются после обработки очереди и фонового анализа; повтор того же исторического окна не гарантирует нового уведомления.

## Настройки окружения

| Переменная | Назначение |
|---|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Подключение к PostgreSQL |
| `RABBITMQ_USER`, `RABBITMQ_PASSWORD` | Учётная запись RabbitMQ |
| `ADMIN_PASSWORD`, `OPERATOR_PASSWORD` | Первоначальные пароли демонстрационных пользователей |
| `INTERNAL_TOKEN` | Авторизация внутренних запросов телеметрии |
| `APP_PORT` | Порт приложения на хосте, по умолчанию `8080` |
| `APP_ORIGIN` | Разрешённый адрес интерфейса для проверок Origin/CSRF и WebSocket |
| `COOKIE_SECURE` | Использование защищённой cookie при HTTPS |

При смене порта, например на `8090`, задайте **обе** переменные:

```dotenv
APP_PORT=8090
APP_ORIGIN=http://localhost:8090
```

По умолчанию приложение доступно только на `127.0.0.1`; порты PostgreSQL, RabbitMQ и ML-сервиса наружу не опубликованы. Пароли БД и брокера подставляются в URL подключения, поэтому при ручной настройке используйте URL-безопасные значения. Скрипт создания `.env` генерирует подходящие значения автоматически.

## Управление и диагностика

```sh
# Состояние контейнеров
docker compose ps

# Последние сообщения сервисов
docker compose logs --tail 100 api-service ingest-service data-worker ml-analyzer

# Пересобрать и запустить приложение после изменений
docker compose up -d --build

# Остановить приложение и удалить контейнеры, сохранив данные
docker compose down
```

Данные PostgreSQL и RabbitMQ хранятся в именованных томах Docker. Для обычной остановки **не добавляйте `-v`**: этот параметр удаляет тома вместе с данными.

Контейнеры `migrate` и `seed` должны завершаться с кодом `0`: это разовые команды, им не требуется постоянно работать. Остальные сервисы имеют проверки готовности.

Если страница не открывается, проверьте состояние Docker, результат `docker compose ps` и журналы. Если измерений нет, проверьте состояние симуляции, сервиса приёма и обработчика. При ошибке входа сверяйте пароль с текущей учётной записью в БД, а не только с изменённым `.env`.

## Проверки без установки браузера

Для регрессионной проверки с нуля используйте ту же команду, что и в CI:

```sh
python3 scripts/run_stack_check.py smoke
```

Она запускает отдельный проект Compose со своим портом, учётными данными и томами.
После проверки временный стенд удаляется. Проверка остановки ждёт состояния `stopped`.

После запуска стека:

```sh
# Проверка Compose
docker compose config -q

# Основные сценарии API, роли, ручные записи и симулятор
python3 scripts/smoke.py

# Управление пользователями и изоляция ферм
python3 scripts/check_users.py
```

Отдельная проверка WebSocket требует работающей симуляции:

```sh
python3 scripts/check_stream.py
```

Скрипты используют обычные HTTP-запросы и `curl`; браузер для них не требуется. Проверки создают учебные записи, а проверка пользователей — тестового пользователя и изолированную ферму. Запускайте их на демонстрационном окружении.

Дополнительные сценарии:

| Команда | Действие |
|---|---|
| `python3 scripts/check_delivery.py` | Проверяет дубликаты, порядок событий и сбои; **временно останавливает и восстанавливает ML-сервис и RabbitMQ**. Требует уже созданной симуляции |
| `python3 scripts/run_stack_check.py load_check --output .cache/load-200.json` | Запускает замер на отдельном стенде: 200 животных, 30 секунд прогрева и 10 минут измерений |

Отчёт о нагрузке содержит параметры Docker, частоты измерений, число сохранённых
показаний конкретной симуляции, частоту и ошибки HTTP-запросов, медиану и p95
ответов списка животных. В `docs/load-report.json` сохранён предыдущий короткий
прогон. Для новых результатов используйте локальный путь из примера.

### Проверки компонентов

Из корня репозитория, при установленных Go и Node.js:

```sh
(cd services && go test ./... && go vet ./...)
(cd frontend && npm ci && npm run lint && npm run build)
```

Проверки ML внутри работающего контейнера:

```sh
docker compose exec -T ml-service python -m pytest -q
docker compose exec -T ml-service python -m ruff check .
```

В репозитории также есть сценарии Playwright. Они не входят в приведённые проверки без браузера; их наличие не означает, что интерфейс уже проверен в браузере.

## Локальная разработка

- Исходники Go-сервисов находятся в одном модуле `services/`; отдельные исполняемые программы — в `services/cmd/`.
- Для разработки интерфейса запустите стек, затем выполните `npm ci` и `npm run dev` из `frontend/`. Для входа через Vite по адресу `http://localhost:5173` задайте `APP_ORIGIN=http://localhost:5173` и пересоздайте `api-service` командой `docker compose up -d api-service`. Прокси Vite по умолчанию обращается к API через порт `8080`; при другом `APP_PORT` скорректируйте `frontend/vite.config.ts`. Для возврата к интерфейсу Nginx восстановите `APP_ORIGIN=http://localhost:8080` (или свой порт) и пересоздайте `api-service`.
- После изменения API обновляйте описание, генератор спецификации, типы и потребителей вместе:

```sh
python3 scripts/generate_openapi.py
(cd frontend && npm run generate:api)
```

- Изменения схемы БД оформляйте новой SQL-миграцией. Уже применённые миграции не редактируйте; API не изменяет схему самостоятельно.

При наличии `make` доступны сокращения: `make up`, `make down`, `make check`, `make test`, `make smoke`, `make api-types`. Команды проверок требуют зависимостей соответствующих компонентов; `make test` также обращается к запущенному демонстрационному стеку.

## Состояние и ограничения MVP

Основные сценарии приложения реализованы и проверялись через HTTP: авторизация, права, телеметрия, ручные записи, уведомления и управление симуляциями. Это не означает завершения всех приёмочных и нагрузочных проверок.

- Модель обучена на синтетических признаках; клиническая оценка и обучение на реальном лицензированном наборе данных не выполнялись.
- Результаты завершённых окон анализа не пересчитываются автоматически при позднем поступлении исторических измерений.
- Воспроизведение ограничено 1000 записями на запуск. После перезапуска процесса неоднозначный активный запуск отмечается ошибкой; гарантированного продолжения с прежней позиции нет.
- Браузерное поведение, доступность интерфейса и исправления из UX-аудита ещё требуют отдельной проверки и работы.
- Расширенная нагрузка на 1000 животных и восстановление из резервной копии не проверены. Короткий локальный замер на 200 животных не является гарантией производительности.
- Публичное развёртывание с TLS не входит в текущую локальную конфигурацию. При публикации потребуются HTTPS, соответствующий `APP_ORIGIN` и `COOKIE_SECURE=true`.

## Ближайшие доработки

Подробные проблемы, задачи, зависимости и критерии готовности собраны в [плане доработки](docs/improvement-plan.md). Все задачи этого плана пока открыты: они не входят в список уже выполненных возможностей.

| Очередь | Что дорабатываем |
|---|---|
| **P0 — сначала** | Изолированные регрессионные проверки; корректные ошибки авторизации и загрузки; доставка телеметрии при длительном отказе БД; маршрутизация обязательных событий |
| **P1 — затем** | Управляемость симулятора и пауза; принадлежность событий запуску; обучение ML на временных рядах; версии и расписание анализа; идемпотентность ручных записей; соответствие OpenAPI |
| **P2 — после** | Поиск и live-обновления; доступность интерфейса; диагностика и аудит; нагрузка на 200/1000 животных; обслуживание данных и восстановление |

В текущем коде обнаружены конкретные ограничения: ошибка БД при проверке сессии может возвращаться как `401`, сбой загрузки может сопровождаться пустой выдачей, а временный сбой записи расходует лимит повторных доставок RabbitMQ. Устранение этих ситуаций приоритетнее новых экранов.

Целевое поведение паузы согласовано: время на паузе **не должно** уменьшать оставшуюся длительность и продвигать replay. Сейчас это ещё не реализовано; задача **P1-02** включена в план.
